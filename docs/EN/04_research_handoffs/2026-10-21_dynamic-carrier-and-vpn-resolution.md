## 1. Core Mission Background and Objectives

In the in-depth research on status bar carrier customization on iOS 27 devices, two core pain points existed:
1. **Ultimate Goal of Dynamic Carrier**: Users desire to "modify only the carrier name, while network radio type (5G/LTE), real-time signal bars, and Airplane Mode auto-hiding maintain 100% dynamic synchronization with the device's native baseband".
2. **VPN Badge Disappearance Defect Under StatusBarOverrides**: Following deployment of `StatusBarOverrides.archive` generated by existing community tools (such as GoldenNugget and early AirLift), when users connect to a VPN, the **VPN icon in the status bar or Control Center completely vanishes**, disrupting the integrity of network status awareness.

This document consolidates all assembly evidence, theoretical final verdicts, and the architectural fix and tooling implementation for the VPN badge issue resulting from this reverse engineering effort.

## 2. Dynamic Carrier (Airplane Mode Synchronization & Live Signal) Reverse Engineering Final Verdict

### 2.1 Low-Level Atomic Replacement Proof of Status Bar Override Layer (StatusBarOverrides.archive)

The community once proposed a "Partial Overwrite" hypothesis, positing that by simply omitting `displayValue` (signal bars) and `type` (radio type) in `StatusBarOverrides.archive`, SpringBoard would fall back to reading authentic baseband signal and radio type text.

We conducted an in-depth disassembly analysis of `SystemStatus.framework` and `SystemStatusServer.framework` within the iOS 27 dyld shared cache:

#### Assembly Analysis 1: `-[STStatusBarDataCellularEntry initWithCoder:]` (`0x20e4a5a5c`)
```assembly
; 0x20e4a5a5c: -[STStatusBarDataCellularEntry initWithCoder:]
mov     x0, x19                 ; self
mov     x1, x20                 ; decoder
bl      0x20e4b8100             ; [super initWithCoder:decoder] (decodes generic fields like enabled, status)

; Decode displayValue (qword)
adrp    x8, 0x20e501000
ldr     x2, [x8, #0x280]        ; @"displayValue"
mov     x0, x20
bl      0x20e4b9310             ; [decoder decodeInt64ForKey:@"displayValue"]
str     x0, [x19, #0x28]        ; store to ivar _displayValue

; Decode type (qword)
adrp    x8, 0x20e501000
ldr     x2, [x8, #0x290]        ; @"type"
mov     x0, x20
bl      0x20e4b9310             ; [decoder decodeInt64ForKey:@"type"]
str     x0, [x19, #0x30]        ; store to ivar _type
```
- **Key Discovery**: When a key is missing, `decodeInt64ForKey:` strictly adheres to Cocoa specifications by returning the primitive default value `0`, rather than **retaining any "pass-through / fallback" sentinel flag**.
- When `displayValue = 0`, the rendering pipeline interprets it as "0 signal bars" or falls back under certain fault-tolerant logic; however, `type = 0` is directly interpreted as `STStatusBarDataNetworkTypeNone`, causing 5G/LTE radio type text to be completely erased.

#### Assembly Analysis 2: `-[STStatusBarData dataByApplyingOverlay:]` (`0x20e4ac960`)
```assembly
; 0x20e4ac960: -[STStatusBarData dataByApplyingOverlay:]
; Check if overlay has cellularEntry
mov     x0, x20                 ; overlay
bl      0x20e4ad110             ; [overlay cellularEntry]
cbz     x0, L_skip_cellular

; If cellularEntry exists, directly overwrite target object pointer
mov     x2, x0                  ; overlayCellularEntry
mov     x0, x19                 ; target copy
adrp    x8, 0x20e502000
ldr     x1, [x8, #0x450]        ; @selector(setCellularEntry:)
bl      0x20e4ba000             ; objc_msgSend(target, @selector(setCellularEntry:), overlayCellularEntry)
```
- **Mathematical and Architectural Conclusion**:
  When `STStatusBarData` applies an overlay, it executes **pointer-level full replacement using the Entry object as the atomic unit**, with zero field-level merging logic.
  As long as `cellularEntry` is injected, the native baseband real-time entry published by `STStatusBarDataPublisher` (subscribed from Telephony/CommCenter) is overwritten as an indivisible whole.

#### 2.2 Why `--partial` Cannot Resolve Airplane Mode Synchronization
- To display a custom carrier name, `cellularEntry` must declare `enabled = YES` and `status = 5` (network registered and ready).
- Once `enabled = YES, status = 5` is declared, even if Airplane Mode is enabled, the static archive loaded persistently by SpringBoard at boot consistently broadcasts to the status bar pipeline that "cellular network is ready and name is the custom text".
- Empirical testing demonstrates:
  - Using `--partial`: Although the lock screen or specific views may display partial baseband bar counts due to `displayValue=0` fault tolerance, radio type text is completely suppressed (no 5G displayed), and under Airplane Mode, **the carrier name remains persistent and does not disappear**.
  - **Conclusion**: `--partial` represents an undefined and fragile boundary condition that degrades radio type display without achieving Airplane Mode synchronization; **it is not recommended for production environments**.

### 2.3 Security Boundary Verification of Upstream Baseband (CommCenter / Telephony) Path
To pursue true dynamic real-time synchronization, we explored the upstream path (resolving the carrier name at the CommCenter level):
1. **CommCenter Privilege Isolation**:
   The `CommCenter` daemon runs under dedicated user `_wireless` (UID 257), storing its actual preferences and cache in `/var/wireless/Library/Preferences/`.
2. **Sandbox and Backup Boundaries**:
   - Non-jailbroken vectors (e.g. MobileBackup2 backup restore, AirLift AirTraffic traversal) operate solely within the `mobile` (UID 501) context, possessing write capabilities restricted to `HomeDomain` (`/var/mobile/`), with mandatory sandbox isolation from `/var/wireless/` preventing any read or write access.
   - On physical devices (iOS 27.0.1), injecting `InterCarrierRoamingDisplayNames` and `CarrierName` across 12 domains under `/var/mobile/Library/Preferences/` proved that even after cold restarting cfprefsd and CommCenter in userspace, upstream baseband continued to read directly from the read-only system image `/System/Library/Carrier Bundles/`, completely ignoring forged configurations in the user directory.
3. **SSV Signature Enforcement**:
   Under iOS 27, `/System/Library/Carrier Bundles/` resides on the SSV (Sealed System Volume), and baseband handshakes enforce `VerifyCarrierBundles = TRUE` strong validation; externally loaded unsigned carrier bundles are rejected directly by baseband hardware.

### 2.4 Final Verdict Summary
On iOS 27 (without jailbreak / without TrollStore / without kernel execution privileges):
> **No purely static file injection approach (including StatusBarOverrides and backup restore) can architecturally achieve the triad of "single-SIM custom name + authentic dynamic baseband signal + Airplane Mode auto-hiding".**
> 
> To achieve this effect, the system would require a resident daemon with `com.apple.systemstatus.publisher` entitlement to dynamically issue Publish requests based on CoreTelephony notifications at runtime — an outcome mathematically unreachable under non-jailbroken sandbox constraints.
> 
> **Dual-SIM Best Practice**: Dual-SIM (including eSIM) users can configure the secondary SIM as a dedicated custom slot while retaining native settings for the primary SIM, thereby achieving harmonious coexistence of native primary signal / Airplane Mode synchronization alongside personalized secondary text display.

## 3. Resolution of VPN Badge Loss Under StatusBarOverrides

### 3.1 Problem Identification and Root-Cause Analysis
Analysis of GoldenNugget and historical archive generation logic revealed two fatal flaws in their generated `_SBSystemStatusStatusBarOverridesArchiveRecord`:

1. **Erroneous Suppression in `suppressedBackgroundActivityIdentifiers`**:
   In early archives, some tools wrote `com.apple.systemstatus.status-item.VPN` or the full set into `suppressedBackgroundActivityIdentifiers` to suppress background activity pills.
   Upon decoding, SpringBoard directly invokes `[STStatusBarOverridesStatusDomainData suppressedBackgroundActivityIdentifiers]`, instructing the UI pipeline to forcibly suppress and hide all badges belonging to VPN activities.
2. **`vpnEntry` Overlay Contamination**:
   Certain tools initialized all entries by default when generating `STStatusBarData` (including `vpnEntry`), but with internal fields set to `enabled = NO` or incomplete structures.
   As established, `dataByApplyingOverlay:` overwrites entire entries by pointer, causing the active VPN Entry published by native `STStatusBarDataPublisher` to be statically overridden to "disabled", resulting in permanent loss of the VPN badge in Control Center and the top-right status bar.

### 3.2 Architectural Fix Mechanism
To allow the VPN badge to render flawlessly, **precise isolation and native pass-through** must be implemented within the NSKeyedArchiver structure:

#### Solution Design:
1. **`auto` Mode (Default, Native Pass-Through Mode, Completely Resolves GN Defect)**:
   - Strictly sets `suppressedBackgroundActivityIdentifiers` to an empty set (`$classes: ["NSSet", "NSObject"]`, `NS.objects = []`), never suppressing VPN status items.
   - **Completely omits the `vpnEntry` key within `STStatusBarData`** (i.e. dictionary contains no `vpnEntry`).
   - **Runtime Principle**: When SpringBoard executes `-[STStatusBarData dataByApplyingOverlay:]`, detecting `vpnEntry == nil` in the Overlay triggers the `cbz` branch, **completely preserving the state published by the system's authentic VPN daemon**. The badge illuminates normally when VPN is connected and hides cleanly when disconnected.
2. **`on` Mode (Forced Persistent Mode)**:
   - Explicitly constructs and serializes `vpnEntry`:
     ```json
     {
       "$class": "STStatusBarDataEntry",
       "enabled": true
     }
     ```
   - Regardless of VPN connectivity, the VPN badge remains permanently visible in the status bar and Control Center (satisfying specific aesthetic user preferences).
3. **`off` Mode (Forced Suppression Mode)**:
   - Explicitly serializes `vpnEntry` (`enabled = false`) or explicitly suppresses it, forcibly hiding the VPN icon.

## 4. Toolchain Implementation and Deliverables

This update has been fully synchronized across all repository tooling components:

### 4.1 Core Generator (`tools/generate_statusbar_archive.py`)
- Function `build_cellular_archive` adds `vpn: Optional[bool] = None` parameter:
  - `vpn=None`: Omits `vpnEntry`, maintains `suppressedBackgroundActivityIdentifiers` as empty set, achieving 100% native pass-through.
